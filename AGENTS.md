# AGENTS.md — working agreement for this repository

Read this before touching anything. It is the short version of the project's
conventions; `docs/RECOVERY.md` is the long version for a cold start.

---

## 1. Git rules (non-negotiable)

- **One branch: `main`.** No feature branches, no temp branches, no
  `gh-pages`, no worktrees that produce extra remote branches.
- Pages deploys from `main` via GitHub Actions. Never create a deploy branch.
- Commit and push after **every** stable slice. Never leave hours of work
  unpushed — the build sandbox is disposable and can vanish without warning.
- Before pushing, check for secrets and for accidental large artifacts
  (`.godot/`, `*.tmp`, editor caches are gitignored — keep it that way).
- Conventional commit prefixes: `feat:`, `fix:`, `perf:`, `build:`, `docs:`,
  `refactor:`, `chore:`.

## 2. What the game is

Original cinematic side-view parkour runner. **2.5D**: gameplay is a 2D plane,
rendering is Godot 3D. See `README.md` for the directory map.

Hard rule: no assets, art, animation, audio, layouts, UI, or code copied from
any commercial game. The reference genre informs *feel*, never content.

## 3. Architecture conventions

- **Typed GDScript.** `class_name` on anything reusable. Annotate parameters
  and returns. `@export` for tunables so they can be adjusted without code
  edits.
- **Player controller is a state machine.** One file per state under
  `game/src/player/states/`. States must not reach into each other; they
  request transitions through the machine. If a state file grows past ~150
  lines it is doing too much.
- **Sensing is separate from acting.** `game/src/player/sensors/` owns all
  raycast/shapecast probing and obstacle classification. States consume a
  read-only snapshot of sensor results. Never raycast inline in a state.
- **Gameplay is authoritative over animation.** Animation never drives
  collision or position except via explicitly opted-in root motion on
  traversal states. A missing animation must never break movement.
- **Movement tunables live in one resource** (`MovementProfile`) so feel can
  be tuned in one place and A/B compared.
- No monolithic files. No dead code — delete it. No speculative abstraction.
  No TODO chains that never resolve.

## 4. Art pipeline

- All art is **generated by headless Blender Python** in `blender/scripts/`,
  exported to glTF/GLB under `game/assets/`.
- A hand-edited `.blend` that cannot be regenerated from a script is a bug.
- Regenerate everything with `./scripts/build_assets.sh`.
- Visual mesh and collision shape are separate. Collision stays coarse and
  predictable; visuals can be detailed.

## 5. Commands

```bash
./scripts/validate.sh        # import + parse every script + boot the main scene
./scripts/test_headless.sh   # autopilot bot must complete the level  <- main gate
./scripts/export_web.sh      # export to exports/web/ and verify the artefacts
./scripts/serve_web.sh       # local HTTP server for the export
./scripts/test_web.sh        # real Chromium/WebGL2 run, bot driving, screenshots
./scripts/test_mobile.sh     # touch controls across 5 phone/tablet form factors
./scripts/shots.sh           # fast deterministic in-engine frames (seconds)
```

Every one of these must exit non-zero on failure. If you make them lenient you
have broken the only safety net.

**Which capture tool to use.** `shots.sh` renders deterministic frames from fixed
stations in seconds — use it for all visual iteration and for before/after
regression comparison. It renders with a desktop GL driver, so it proves nothing
about the browser. `test_web.sh` is the honest end-to-end check and takes minutes.
Iterate with the first, verify with the second.

## 5a. Input rules

- **Never read input in `_input`/`_unhandled_input` with `event.is_action_*`.**
  The touch controls drive the game via `Input.action_press()`, which sets action
  state without synthesising an `InputEvent`. Event-based handlers are invisible
  to touch. Poll `Input.is_action_just_pressed()` instead — it sees keyboard,
  gamepad and touch identically.
- Gameplay input is latched in `PlayerInput._physics_process`, never `_process`.
  The controller runs on the physics tick and must sample on the same clock.
- Touch is a supported platform. Any new action needs an on-screen control in
  `src/ui/touch_controls.gd`, and buttons must *hold* their action rather than
  pulse it, or variable jump height and sustained slides break.
- **The HUD never occupies a thumb corner.** Meters live permanently top-left
  under the timer. An earlier design moved them out of the way when the touch
  controls appeared; that conditional layout was wrong in practice and resisted
  two fixes, so it was deleted. One position that is always correct beats a
  clever one that is sometimes correct.
- **Browser touch detection is unreliable and must not be trusted alone.**
  Desktop Chromium reports a touchscreen as available *and* delivers mouse
  clicks as `InputEventScreenTouch`. Detection uses the user agent on web,
  retreats on real mouse/keyboard input, and is overridable via
  `Game.touch_mode` (`?touch=0` / `?touch=1` in the URL). Any auto-reveal path
  must respect an explicit override — that is exactly where it broke before.

## 6. Testing philosophy

Code compiling proves nothing. Every milestone must:

1. validate headlessly,
2. export to web,
3. actually load in a real browser,
4. be **screenshotted and reviewed by at least 3 independent vision critics**
   with distinct roles (visual quality / animation & movement / gameplay
   readability / genre feel / browser-technical),
5. have the top-ranked issues fixed and re-verified with before/after captures.

The builder is never the only reviewer of its own output.

Priority order when triaging critic findings:
broken gameplay → traversal & collision → animation → camera & readability →
browser/export → visual quality → polish.

## 7. Known pitfalls

- **Web export must have thread support OFF.** GitHub Pages cannot send
  COOP/COEP headers, so `SharedArrayBuffer` is unavailable and a
  threads-enabled build will fail to boot. The preset in
  `game/export_presets.cfg` already has `variant/thread_support=false`.
- **The export must be served over HTTP.** `file://` cannot load the WASM.
- **Renderer is `gl_compatibility`.** Forward+/Mobile need WebGPU, which is
  not reliably available. Do not use features that silently no-op on
  compatibility (SDFGI, SSAO, volumetric fog, `SCREEN_TEXTURE` blur chains).
- **`godot --headless --import` may need two passes** on a cold `.godot/`
  cache before all resources resolve. `validate.sh` handles this.
- **Blender needs `libGL`** even with `--background`; install mesa libs first.
- **Never commit `.godot/`** — it is a multi-hundred-MB derived cache.
- Web builds are sensitive to total size. Watch `exports/web/*.pck`.
